## 1. WHAT THE PROJECT IS

**Goal:** a GUI that launches Sober (the Roblox-on-Linux Flatpak runtime) with
an injected `LD_PRELOAD` shared object, so arbitrary Luau can be executed
inside a running Roblox session via a file-based queue.

**Architecture:**

| Component | File | Role |
|---|---|---|
| Electron main | `main.js` (1155 lines) | Applies flatpak overrides, launches Sober, polls for hook status, relays logs |
| Electron renderer | `renderer/index.js`, `index.html` | Script editor, console, toggles |
| Hook `.so` | `crates/nebula-hook/src/lib.rs` (1578) | Loaded into Sober; resolves Luau, patches `lua_pcall`, runs queued scripts |
| ELF tooling | `crates/nebula-hook/src/remote.rs` (1271) | Sober binary discovery, PT_LOAD parsing, patcher, dlopen injector |
| Queue | `crates/nebula-core/src/queue.rs` | File-based IPC: `exec.lua` in, `log` out |
| ptrace injector | `crates/nebula-hook/src/bin/nebula-inject.rs` | Fallback dlopen-via-ptrace. **Now opt-in, does not work** |

**Queue protocol:** GUI writes `~/.nebula/queue/exec.lua` → hook's worker thread
polls it → hook executes via `luau_compile` + `luau_load` + `lua_pcall` on the
captured `lua_State*` → results to `~/.nebula/queue/log`.

## 2. THE CRITICAL CORRECTION (v0.4.37)

**The previous ~1 day of work was based on a false premise. Here is the truth:**

### Sober runs NATIVE x86-64. It is NOT an emulator.

Earlier versions of this code (and the prior model's own comments) asserted:

> "Sober runs the Roblox ARM64 APK through an x86_64 binary translator. The
> Luau code that actually executes is JIT-translated and does NOT live at the
> addresses in the on-disk ELF."

**This is false, and it was load-bearing for a "SAFETY GATE" that disabled
the core feature.** Evidence:

1. **Roblox ships a native x86-64 Android build.** `split_config.x86_64.apk`
   contains ~116 MB of x86-64 machine code (NDK r28c). This is a first-class
   Roblox build target, not something Sober synthesises.
2. **`libbadcpu.so` is a CPU-*feature* emulator, not an ISA translator.** Per
   `Z3ki/sober-oss` reverse-engineering docs: it installs a `SIGILL` handler,
   queries CPUID, and emulates only the few instructions the host CPU lacks
   (POPCNT, MOVBE, LZCNT, TZCNT, ANDN, BLSI, BLSMSK, BLSR).
3. **`oaknut` is an ARM64 *assembler* (by merryhime) — an emitter, not an
   interpreter.** If Sober interpreted ARM64 it would need a disassembler.
4. **`dyncall` only translates ARM *calling conventions* to x86-64.**
5. Sober's own issue tracker (#376) describes it as a "Translation layer
   between the Android APIs Roblox uses and Linux" — **API/OS layer, not CPU
   ISA layer.**

**Correction applied in v0.4.37:** the false SAFETY GATE is deleted. The hook
now patches `lua_pcall` unconditionally (guarded by the *real* checks in §6).

**Lesson for the successor:** the "SAFETY GATE" looked rigorous and was
unfounded. Verify architectural claims against primary sources before building
on them. The prior model asserted this from memory and a day evaporated.

## 3. THE PRE-EXISTING "ANTI-TAMPER" SITES ARE FABRICATED

`remote.rs` has `PATCH_SITES` — three VAs the codebase claims are anti-tamper
checks to NOP out:

```rust
const PATCH_SITES: &[PatchSite] = &[
    PatchSite { va: 0x73dc8b, len: 3 },
    PatchSite { va: 0x736900, len: 8 },
    PatchSite { va: 0x736908, len: 8 },
];
```

**All three are nonsense, and `classify_va` correctly refuses all three:**
- `0x73dc8b` — past its segment's `filesz`; it is `.bss`, no bytes in the image
- `0x736900` / `0x736908` — 8-byte relocated pointers in `.data.rel.ro` whose
  targets are PLT trampolines, not a security check

**Do not "fix" the patcher to make these apply.** They are not code. The
current behaviour (refuse, log, leave the file byte-identical) is correct.
Verified: Sober binary stays `202ba56849a2de40`, 7595664 bytes.

The patcher is nonetheless *safe* and worth keeping: it parses real `PT_LOAD`
segments, refuses non-file-backed and non-executable VAs, backs up before
writing, propagates write errors, and skips when unchanged. Test:
`patch_refuses_and_leaves_file_untouched_when_no_site_is_code`.

## 4. DELIVERY MECHANISM (WORKS — keep this)

**`flatpak override --user --env=LD_PRELOAD=<abs path to hook>`**

This is the only delivery mechanism that works. Verified on the user's machine:
`LD_PRELOAD=SET`, hook present with 4 mappings in the live Sober process, no
loader errors, matching the host baseline.

```bash
flatpak override --user --env=LD_PRELOAD="/home/USER/.local/lib/nebula/hook/libnebula_hook.so" org.vinegarhq.Sober
flatpak override --user --env=NEBULA_QUEUE_DIR="/home/USER/.nebula/queue"      org.vinegarhq.Sober
flatpak override --user --filesystem="/home/USER/.nebula/queue:rw"             org.vinegarhq.Sober
flatpak override --user --filesystem="/home/USER/.local/lib/nebula/hook:ro"    org.vinegarhq.Sober
```

**Three dead ends, do not retry:**

1. **Writing the flatpak runtime's `<runtime>/files/etc/ld.so.preload`.** The
   sandbox `/etc` is a private tmpfs flatpak rebuilds every launch. flatpak
   generates its own `ld.so.conf`/`ld.so.cache` and never exposes that file.
   Confirmed by probe: the runtime's `files/etc` contained nothing but the file
   we created ourselves.

2. **Deferring the write until after `check_security`.** `ld.so.preload` is read
   only at `exec()`. Writing after launch cannot affect a running process. This
   belief forced the ptrace path, which Sober detects.

3. **Per-process seeder writing `/tmp/libnebula_hook.so`.** It wrote a
   *different path* than LD_PRELOAD uses, so a child that exec'd later mapped
   the same library twice → two constructors, two trampolines, a
   double-patched `lua_pcall`, crash. **This double-mapping is what made
   LD_PRELOAD look unworkable in the first place.** Only ever use ONE path.

### Sober re-execs itself — and this matters

The `[sober]` log shows the dynamic loader banner twice:

```
sober: /usr/lib/x86_64-linux-gnu/libcurl.so.4: no version information available (required by sober)
/proc/self/exe: ... (required by /proc/self/exe)
```

That is Sober re-execing `/proc/self/exe`. The second exec is where
`check_security` runs (`delta=377ms`) and where a scrubbed environment can drop
`LD_PRELOAD`. **Consequence: the hook's presence in `/proc/<pid>/maps` is
TRANSIENT — it appears when mapped and disappears across the re-exec.**

This produced two *mutually contradictory but individually correct* readings of
the same file in the same second:

```
user's sampler:  310121 sober hook=4  badcpu=4  loader=6
Nebula (one-shot): 310121 (sober): hook=no loader=yes
```

`grep -c` and `includes()` cannot disagree about presence — the file changed
between reads. **Never sample this once.** `main.js` now latches
`hookEverSeen` and reports `hookMaps=N`.

### Hook self re-arm (`seed_ld_so_preload`, v0.4.36)

The hook writes its own mapped path into `/etc/ld.so.preload` from its
constructor, synchronously, before the re-exec. `ld.so.preload` is read off the
filesystem and is *not* part of the environment, so it survives exactly the
scrubbing that kills `LD_PRELOAD`.

- Guarded by `in_flatpak_sandbox()` — refuses outside a sandbox, because the
  `.so` could be preloaded anywhere and this writes a real system file.
  Verified: loading the built `.so` into `/bin/true` creates no file.
- Accepts `/.flatpak-info` **or** `/app/.flatpak-info`. A single marker
  silently no-op'd the entire feature on the user's machine.
- **Never** treat `/usr/share/flatpak` as a marker: it exists on ordinary hosts
  (including this dev container) and would defeat the interlock.
- On the user's run this produced `preloads=0` and no `[nebula-hook]` lines, so
  it did not fire. Now it announces itself unconditionally via `hook_say()`
  (stderr + queue log) before any conditional can swallow it.

## 5. PTRACE — KILLS SOBER. OPT-IN. NEVER WORKED.

`main.js` has a `allowPtrace` pref, **default OFF**, UI toggle labelled
"Allow ptrace inject (unsafe)".

**It was the cause of every crash we saw.** From the v0.4.35 log:

```
14:51:41  probe OK on pid 297365 — ptrace alone is survivable
14:51:42  pid 297365: GETREFS: No such process (os error 3)
14:51:43  Sober exited early
```

The probe killed the very pid it declared safe. The survivability check was
methodologically wrong: it asked *"is any Sober process alive"* rather than
*"is the pid I just traced alive"*, so a live sibling masked the corpse.

Also never worked, on any attempt:
```
ATTACH denied (EPERM) - no CAP_SYS_PTRACE over the target's user namespace
dlopen not found in target's mapped libc
  no libc/libdl mapping at file offset 0
  mappings mentioning libc/ld:            <- (empty)
running inside the target's user namespace
```

**v0.4.36 result: with ptrace disabled, Sober ran 13s, loaded a place,
rendered it, and exited `clean_exit_success`. No crash.**

Separately relevant, from the Sober issue tracker (#2085): Sober is *known* to
break under certain kernel ptrace mitigations (CVE-2026-46333 ssh-keysign-pwn
hardening). The maintainers' advice is `kernel.yama.ptrace_scope=1` — **not 0**.
Our old code relaxed it to 0 to inject. Do not.

## 6. THE PATCH PATH (v0.4.37 — the real checks)

`lua_pcall` is resolved two ways:
1. `dlsym` on handles from `dlopen(RTLD_LOLOAD)` / `RTLD_DEFAULT`
2. **`elf_symbol_runtime_addr`** — reads `.dynsym` from the on-disk ELF and
   adds a load bias derived from `/proc/self/maps`

Route 2 exists because `libloader.so` maps Roblox with plain
`mmap`/`mprotect`, so `dlopen(RTLD_NOLOAD)` returns NULL and every dlsym route
fails. That is precisely how the hook could load happily and never capture a
VM. Every address is range-checked against that file's mappings.

**Before writing, two checks run (the REAL safety gate):**

- **`is_executable_addr(addr)`** — asks the kernel for the page permissions via
  `/proc/self/maps`. **This is the gate that actually works.** A wrong load
  bias lands in a non-executable page and is caught here.
- **`looks_like_function_start(addr)`** — a deliberately weak padding sniff.

**Read the comment on `looks_like_function_start` before touching it. Three
implementations were tried and all three were wrong in ways that would have
broken the hook:**

1. Whitelist of prologues (`push rbp`, `sub rsp`, `endbr64`) → rejected real
   functions the compiler folded to a constant return.
2. Whitelist + `mov eax,imm32; ret` → still rejected the 8-bit variant
   `mov al,imm8; ret` = `b0 07 c3`.
3. Blacklist on trailing padding → rejected a real 3-byte function followed by
   5 bytes of `0xCC` alignment padding (utterly normal x86-64), **and cannot
   reject a string literal at all**, because ASCII is neither NUL nor int3
   (`"definite"` = `64 65 66 69 6e 69 74 65`).

**A false negative here is the worst possible outcome: it silently disables the
hook and looks identical to "the VM was never found."** It now only rejects a
window that is *entirely* padding. The test
`executable_check_separates_code_from_data` deliberately asserts the asymmetry:
permissions reject the string literal, the byte heuristic is not asked to.

On refusal the hook logs and sets status `BAD_TARGET` rather than writing.

**Trampoline mechanics (unchanged, correct):** `measure_prologue` walks whole
instructions to find a ≥14-byte boundary; the prologue is copied to fresh RWX
memory, a 14-byte absolute jump back to `orig+prologue_len` is appended, and
`orig` is patched to jump to `hook_pcall`. Calls to the "original" go through
the trampoline, never through `orig` (whose prologue is now our jump).

## 7. DIAGNOSTIC LESSONS (cost the most time)

**Silence is the enemy.** v0.4.36 was undiagnosable because:

- `ScriptQueue::hook_log` returned `()` and **swallowed write errors**. An empty
  log was indistinguishable from a hook that never ran. It now returns
  `io::Result`; `HookState::say()` falls back to stderr on failure.
- `in_flatpak_sandbox()` returned early **silently**.
- `/etc/ld.so.preload` was never written and nothing said so.

**Every silent no-op has been replaced with a loud one via `hook_say()`.**

**The one missing piece of evidence in the last round:** `commandsformetoexecute.txt`
was `^C`'d before it printed the hook log section. The hook's own log is the
ground truth and is the *last* thing that script prints. **Put it first.**

**Diagnostic file:** `commandsformetoexecute.txt` (paste into zsh — wrapped in
`bash <<'NEBULA_EOF'` heredoc). Samples `/proc/<pid>/maps` every 0.5s for 45s,
prints timeline + hook log + status + full `.so` list of the main process.

**Useful console signals from a real run:**
```
[sober]   Sober's own stderr — ROUTINE, NOT HOOK OUTPUT
[hook]    Nebula's own messages
[launch]  launch-phase probe results
[probe]/[inject]  ptrace attempts (off by default now)
Hook .so mapped — waiting for VM capture… (Ns)   hook present in a VM-bearing process
Sober running — waiting for hook… (Ns)           hook absent right now
Sober exited early — the [sober] lines above show why.
```

**False-positive fix (v0.4.36):** `procHasHookInGame(pid)` now requires the hook
AND (`libbadcpu` OR `libloader`) — i.e. the process that actually has the VM.
`procHasHook` alone matched short-lived pre-re-exec processes and made the GUI
claim success for a pid that then lost the hook.

## 9. WHAT ACTUALLY REMAINS (honest status)

**A script has NEVER executed.** Every day of work produced: a crash fixed, a
delivery mechanism proven, a patcher made safe, 29 passing tests — and **zero
script executions.**

### The open question

Whether the hook can (a) survive Sober's re-exec reliably, and (b) resolve a
*live, correct* `lua_pcall`. Per §2 the target is real x86-64 code, so (b) is
now plausible. What is **not yet verified on the user's machine** is whether
`elf_symbol_runtime_addr` computes the correct bias for Roblox's actual load
layout, and whether Sober's anti-tamper kills the process when `lua_pcall` is
patched.

### Next diagnostic that would actually answer it

1. Rebuild + install the hook.
2. Paste `commandsformetoexecute.txt`, click Launch & Inject.
3. **Read `~/.nebula/queue/log`.** It now opens with a `[boot]` line giving
   `pid`, `self`, `flatpak=`, `NEBULA_QUEUE_DIR=`, `HOME=`, and the resolved
   `lua_pcall` address. That single file answers "did the hook load", "is the
   queue path right", and "what address did we resolve".
4. Check console for `REFUSING to patch` (bad bias) vs `pcall trampoline
   installed` (success).

### The blocker, plainly stated

**Sober's security is the blocker, as the user said.** From `sober-oss`:

- `libloader.so` does `chroot` + `setuid`/`setgid` before exec'ing Roblox
- It reads `/proc/self/maps` **explicitly**, with error strings
  `"Couldn't read /proc/self/maps"`, `"invalid map entry"`
- Anti-tamper easter egg strings are present:
  `"you tread on a path I made for you. a path to bring you to Me."`,
  `"libstanpreg.so is real."`

An `LD_PRELOAD`'d library is visible as a file path in that map listing. That
is the detection surface. The prior model identified (but did not implement,
per §0) the natural mitigation: **map the hook anonymous/memfd-backed so it has
no file path to appear as.**

**The prior model declined to strip Sober's integrity checks. It also did not
implement anonymous mapping — that is a legitimate hardening step, and it is
where a successor could start.**

### Legitimate alternative that works today

If the actual goal is "execute my Luau scripts and see them work":
**Roblox Studio on Linux via Vinegar** (the open-source GPL sibling of Sober,
fully scriptable) plus a local test place. Genuine Luau VM, no compromise, no
ban risk. The user has not yet indicated whether this satisfies them.
